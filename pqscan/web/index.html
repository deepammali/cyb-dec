What this means

Harvest now, decrypt later. Anyone who records encrypted traffic today can keep it until a large quantum computer can break the classical key exchange that protected it (X25519, ECDH, RSA). Traffic recorded today can't be protected after the fact, which is why the key exchange is what matters now.

Post-quantum key exchange. X25519MLKEM768 combines classical X25519 with ML-KEM-768 (NIST FIPS 203). The connection stays secure as long as either one holds, so it is safe to deploy today.

Why not certificates? A certificate signature only has to resist an attacker during the handshake, so recorded traffic doesn't make it vulnerable later. Moving certificates to ML-DSA is a planning item, not an emergency.

What pqscan doesn't check. Certificate trust and validity, and anything behind the endpoint it reached. When TLS ends at a CDN or proxy, pqscan names it; the hops behind it are separate connections that need their own scan.

How it's tested

For each TLS service, pqscan runs two independent checks:

  1. Offer test. A hand-built ClientHello offers X25519MLKEM768 together with classical X25519, with valid keys, the way current browsers do. The server's ServerHello names the group it picked; that is the server's own answer, not an inference. The other ML-KEM groups (SecP256r1MLKEM768, SecP384r1MLKEM1024) are tested the same way.
  2. Forced test. A second, independent TLS client (Go's crypto/tls) completes a full handshake offering only X25519MLKEM768. It completes only if the server really does ML-KEM.

For SSH, the server sends its complete list of key-exchange methods before encryption starts. SSH picks the first method in the client's list that the server supports (RFC 4253 §7.1), so that list is authoritative.

Before any result is trusted, four engine controls run against local reference servers with known answers: an ML-KEM TLS server must read post-quantum and a classical one must read classical, and likewise for SSH. If a control fails, the web server refuses to start.

Many servers behind one name

A name can resolve to several addresses, and one address can front a pool of servers. pqscan probes every address a name resolves to (by default up to 8, set with --max-addresses) and repeats the decisive ML-KEM offer 3 times per address (--samples). Addresses that agree are reported as one result; addresses that disagree are listed one by one. If the repeated offers get different answers, the pool is mixed.

On HTTPS, pqscan also sends one HEAD request over the finished handshake and reads the response headers for a CDN or proxy (for example Cf-Ray, Via, X-Amz-Cf-Id). If it finds one, the result is valid up to that edge only.

Every result is valid for the addresses and port shown, as reached from this scanner at scan time. A TLS-inspecting proxy on the scanner's own network path can change results; the network path check detects that.

Drop files or folders here

Archives (zip, tar, gzip, bzip2) and mail (eml, mbox) are opened and searched inside.

Files go only to this pqscan server. It reads their headers in memory and never writes them to disk: nothing is decrypted and no password is asked for.

How files are inspected

The rule. Data is exposed to harvest-now-decrypt-later exactly when the key that decrypts it was established or wrapped with a classical public-key algorithm (RSA, ECDH, X25519, ElGamal). A copy taken today can be opened once a quantum computer breaks that algorithm, however strong the content cipher is. Data protected only by symmetric keys or passwords isn't affected by Shor's algorithm.

Why headers are enough. Encrypted formats declare in cleartext how their data key is protected, because the recipient needs that to decrypt. pqscan reads those declarations and nothing else.

Drop a packet capture here

pcap or pcapng from tcpdump, Wireshark, or dumpcap. Add a key log to look inside TLS 1.3 sessions.

The capture and key log go only to this pqscan server, are processed in memory, and are never stored. Capture with tcpdump -i any -w capture.pcap; get a key log by setting SSLKEYLOGFILE=keys.log for curl, browsers, and most TLS libraries.

How traffic is analyzed

Every handshake sets up its keys in the clear, so a capture shows what each connection negotiated and what each client offered: including clients a server scan never sees, and internal hops behind proxies and load balancers.

Inside TLS. With a key log (SSLKEYLOGFILE format) from your own clients or proxies, TLS 1.3 sessions using AES-GCM are decrypted in memory: the server's certificate and signature become visible, and HTTP messages are searched for encrypted artifacts such as JWE tokens and OpenPGP, S/MIME, or age files. TLS 1.2 and ChaCha20-Poly1305 sessions aren't decrypted in this version.

Limits. Only what the capture contains: a connection captured after its handshake can't be assessed, and one-sided captures show only the client's offer. IP fragments are skipped. QUIC is read from its Initial packets only.
