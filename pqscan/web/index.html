What this means

Harvest now, decrypt later. Anyone who records encrypted traffic today can keep it until a large quantum computer can break the classical key exchange that protected it (X25519, ECDH, RSA). Traffic recorded today can't be protected after the fact, which is why the key exchange is what matters now.

Post-quantum key exchange. X25519MLKEM768 combines classical X25519 with ML-KEM-768 (NIST FIPS 203). The connection stays secure as long as either one holds, so it is safe to deploy today.

Why not certificates? A certificate signature only has to resist an attacker during the handshake, so recorded traffic doesn't make it vulnerable later. Moving certificates to ML-DSA is a planning item, not an emergency.

What pqscan doesn't check. Certificate trust and validity, application-layer encryption, and anything behind the endpoint it reached.

How it's tested

For each TLS service, pqscan runs two independent checks:

  1. Offer test. A hand-built ClientHello offers X25519MLKEM768 together with classical X25519, with valid keys, the way current browsers do. The server's ServerHello names the group it picked; that is the server's own answer, not an inference. The other ML-KEM groups (SecP256r1MLKEM768, SecP384r1MLKEM1024) are tested the same way.
  2. Forced test. A second, independent TLS client (Go's crypto/tls) completes a full handshake offering only X25519MLKEM768. It completes only if the server really does ML-KEM.

For SSH, the server sends its complete list of key-exchange methods before encryption starts. SSH picks the first method in the client's list that the server supports (RFC 4253 §7.1), so that list is authoritative.

Before any result is trusted, four engine controls run against local reference servers with known answers: an ML-KEM TLS server must read post-quantum and a classical one must read classical, and likewise for SSH. If a control fails, the web server refuses to start.

Every result is valid for the IP address and port shown, as reached from this scanner at scan time. Other servers behind the same name, or a TLS-inspecting proxy, can behave differently.

pqscan checks key exchange per RFC 8446, draft-ietf-tls-ecdhe-mlkem, and FIPS 203. Everything on this page is served by the scanner itself.
